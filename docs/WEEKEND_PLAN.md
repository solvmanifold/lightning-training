# Weekend Fine-Tuning Methods Comparison

> **Historical plan:** the checked-in pilot reused validation data as its test
> set and had incomplete judge coverage. `README.md` and the current scripts
> describe the hardened protocol for new runs; the old result is not a clean
> method comparison.

Compare four fine-tuning methods on the same dataset and produce a shareable report.

## Methods

1. **SFT LoRA** (already done) — baseline. Standard supervised fine-tuning with BF16 base.
2. **QLoRA** — same as SFT but base model quantized to 4-bit NF4 during training.
3. **DPO** — preference optimization starting from SFT adapter.
4. **GRPO** — RL with rule-based (ROUGE-L) reward starting from SFT adapter.

## Dataset

- 1795 Q&A pairs generated by Nemotron-3-Super over the `~/Dev` codebase.
- New runs use source-grouped train / validation / test partitions produced by
  `prepare.py`. The test partition is never used for checkpoint selection.

## Evaluation Protocol

Consistent across all methods:
1. Load the fine-tuned adapter.
2. Generate a response for each of the 89 test prompts at temperature 0.3, max_tokens=512.
3. Save responses to disk (one JSONL file per method).
4. Start Super as judge.
5. For each (prompt, response, ground_truth) triple, ask Super to score 1–5 on factuality + relevance.
6. Also compute reference-based ROUGE-L against the ground truth.
7. Aggregate: mean judge score, mean ROUGE-L, win rate vs. base model.

Base model (no fine-tuning) is scored once as the floor.

## Design Decisions

- **Reduced training budget per method** (150 steps, grad_accum=2) so each new method fits in ~4 h. The SFT baseline used 500 steps and grad_accum=8 (~22 h) — not strictly fair, but noted in the writeup. Toy comparison, not a paper.
- **DPO preference data**: `chosen` = ground truth from Super-generated dataset; `rejected` = generated by the *base model* (pre-SFT) at temp=0.9 on the same prompt. This teaches DPO to move toward Super-quality answers.
- **GRPO reward**: ROUGE-L F1 against ground truth. Fast, deterministic, no judge in the loop.
- **Starting points**:
  - QLoRA: fresh from base model.
  - DPO: initialized from SFT adapter.
  - GRPO: initialized from SFT adapter.
- **GPU serialization**: Nano training → stop → Nano inference → stop → Super (judge). Only one model loaded at a time.

## Known Risks

- **bitsandbytes on GB10 (SM121)** — may not have kernels. If QLoRA phase fails, skip it; other phases unaffected. Failures are logged but don't abort the rest.
- **GRPO instability** — RL is finicky on MoE models. If it diverges or crashes, the phase fails and we continue with what we have.
- **Super startup time** (~15 min for TRT compile) — scheduled once at the end.
- **Total time overrun** — if earlier phases run long, later phases may start later than planned, but all phases have buffer and can run into Monday morning.

## How To Run

```bash
# Kick off the whole thing (from a tmux session so it survives disconnect)
tmux new -s weekend
cd ~/Dev/nano3-training
bash scripts/run_weekend.sh 2>&1 | tee outputs/weekend.log
# Ctrl+B D to detach. Reattach with: tmux attach -t weekend
```

The script is idempotent — it skips phases whose output already exists, so you can restart it safely after a crash.

## Interpreting the Results

Things to look for:
- Does QLoRA match SFT? If close, argues for QLoRA's memory efficiency.
- Does DPO beat SFT? Shows value of preference optimization even with synthetic preferences.
- Does GRPO overfit to ROUGE? Watch for high ROUGE but low judge score — that's the model gaming the reward.
- Does any method beat SFT on judge score? DPO typically does; GRPO depends on reward quality.
